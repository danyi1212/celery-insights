# Dependency upgrade validation

Upgrade snapshot: 2026-10-02. See [runtime/backend inventory](dependency-upgrade-research.md) and [frontend inventory](frontend-upgrade-research.md) for versions and official migration sources.

## Review boundaries

The combined PR upgrades Bun to 1.4.2, Python image/CI to 3.14.8, SurrealDB to 3.3.0 (Python SDK 2.0.0 / JS SDK 2.0.9), Celery to 5.6.3, the latest resolvable Python dependencies, frontend packages, uv, container base distributions and GitHub Actions. Exact transitive resolutions live in the three committed lockfiles.

Substantial frontend refactors are tracked separately:
- [Table 9 migration #120](https://github.com/danyi1212/celery-insights/issues/120)
- [Joyride 3 migration #121](https://github.com/danyi1212/celery-insights/issues/121)
- [Upstream-constrained optional drivers #122](https://github.com/danyi1212/celery-insights/issues/122)

Unused uuid and its deprecated type stub are removed. Celery's nonexistent Riak extra is removed; other driver bounds follow upstream requirements. Production exports exclude the development dependency group.

## Compatibility adjustments

TypeScript 7 removes baseUrl: paths now use explicit relative targets; the Vite/Vitest alias loader already resolves those relative to the config file. Binary WebSocket payloads are copied into Uint8Array to meet the modern WebSocket BufferSource contract. Router error props now accept the router's actual error type and safely display non-Error throws. A local GitHub SVG preserves the header icon after Lucide removes brand icons.

The latest Ruff drops two obsolete broad-exception suppressions. The latest SurrealDB SDK introduces its own exception hierarchy: initial connection retries now include SurrealError, with a regression case for ConnectionUnavailableError. Cleanup query variables are explicitly typed to the SDK's recursive Value type. Starlette's template module now requires Jinja2 even when imported indirectly by fastapi-cache2; the production dependency is explicit. New third-party loggers are configured.

Oxlint enables new React Compiler-oriented defaults (purity, refs, set-state-in-effect, incompatible-library) that were absent in the baseline lint policy. This project does not enable React Compiler. They are explicitly disabled to preserve the existing policy during the dependency upgrade, as is prefer-tag-over-role: the custom listbox/options and SVG chart roles are intentional. Existing enabled checks remain enforced with --deny-warnings. Enabling the new compiler rules should be a separately reviewed code refactor, not an incidental upgrade change. Oxfmt changes formatting in two existing components; route-tree changes are generated by the updated router plugin.

## Evidence

- Python 3.14.7 locally: backend pytest/doctest suite passes (205 tests before the added SDK retry case); Ruff and ty pass.
- Bun 1.4.2 locally: 50 frontend/runtime test files, 416 tests pass; type/lint/format and production Vite build pass.
- Frozen Bun install and both uv locks resolve; all optional Python groups install locally on macOS arm64.
- Python 3.14.8 is pinned for Docker/CI; the local uv 0.12.17 downloader only lists 3.14.7, so local Python checks alone do not verify the pinned patch.
- Docker Desktop startup requires completion of its macOS administrator prompt. Container builds, browser E2E, persisted-volume upgrade and both architecture builds remain pending CI/local validation.

## Release gate

Do not infer release readiness from unit tests. Require green PR CI, regular/all images on amd64 and arm64, real Celery E2E scenarios, demo/WASM sanity, and persisted database upgrade/backup/replay evidence. Preserve a backup made with the old binary before upgrading a disk-backed SurrealDB instance. SurrealDB 3.1+ adds metadata that can limit downgrades: test restore rather than promising binary-only rollback.

## RabbitMQ 4.3 compatibility

The initial real-container E2E startup failed because RabbitMQ 4.3 rejects non-durable, non-exclusive queues. The monitor now uses exclusive event/control queues unless the user's Celery config explicitly enables durable queues; durable queues stay nonexclusive. The worker harness uses exclusive control queues too. This adopts the queue modes supported by RabbitMQ, without enabling its deprecated feature flag. Upstream Celery 5.6 defaults both exclusive settings to false, so applications running their own workers against RabbitMQ 4.3 should set `control_queue_exclusive = True` (or use durable control queues). [RabbitMQ queue guidance](https://www.rabbitmq.com/docs/queues), [Celery stable configuration](https://docs.celeryq.dev/en/stable/userguide/configuration.html).
