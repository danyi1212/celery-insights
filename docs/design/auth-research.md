# Authentication and authorization research

Research date: **2026-10-02**. Scope: one Celery cluster per installation initially; local accounts plus optional enterprise OIDC; role grants intersected with custom OPA restrictions. This note supplies evidence for the design, not an implementation or a compliance certification. Only official standards, maintainer documentation, and OWASP guidance are cited. No deployed systems were contacted.

## Version and source context

- The repository's `Dockerfile:2` pins **SurrealDB v3.3.0**. Python `surrealdb>=2,<3` and JavaScript `surrealdb ^2.0.9` refer to SDK versions, not the server major version. SurrealDB's online documentation is rolling and explicitly discusses some 3.3.0 capability changes; validate capability flags against the pinned binary before implementation. [Capabilities](https://surrealdb.com/docs/learn/security/authorization/capabilities)
- OPA sources below are its rolling official documentation, including Rego v1 bundle metadata and current compile endpoints. This research does **not** select or verify a particular OPA release. Pin an implementation version and verify these APIs in its integration tests. [Bundles](https://www.openpolicyagent.org/docs/management-bundles)
- Standards: **OpenID Connect Core 1.0 incorporating errata set 2**, **RFC 9700 / BCP 240** (January 2025), and final **NIST SP 800-63B-4**. OWASP cheat sheets are maintained guidance, not normative RFC requirements. [OIDC Core](https://openid.net/specs/openid-connect-core-1_0.html), [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html), [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

## Authentication evidence

**Documented:** OIDC defines authentication over OAuth. Code flow exchanges a code at the token endpoint; confidential clients authenticate there. ID-token validation checks exact issuer, client audience, expiration, and nonce when supplied, with cryptographic validation rules. OIDC's subject claim is the provider's local user identifier. [OIDC Core §§2, 3.1.3](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)

**Documented:** RFC 9700 requires PKCE for public clients and recommends it for confidential clients; `S256` avoids exposing the verifier. Challenges/nonces must be transaction-specific and bound to the initiating user agent. Clients must prevent callback CSRF; multi-provider clients require mix-up defenses. Redirect URIs require exact matching apart from the native-loopback exception. The password grant must not be used. [RFC 9700 §§2.1, 2.4, 4.7](https://www.rfc-editor.org/rfc/rfc9700.html)

**Recommendation:** terminate OIDC in FastAPI using a maintained OIDC client: Authorization Code + PKCE S256, state and nonce bound to a short-lived server login transaction, fixed configured issuers and callbacks, token verification with an algorithm allowlist and provider keys. Store identity by `(issuer, subject)`, never automatically merge accounts solely by matching email. Resolve groups through explicit configured mappings; unknown groups grant nothing. Keep provider tokens on the server and issue the same local opaque application session used for password login.

**Documented:** OWASP recommends secure cookie attributes, server-enforced session expiration, renewal after privilege changes, and invalidation on logout. SameSite is useful but OWASP warns against relying on it alone for CSRF prevention. [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

**Recommendation:** use shared persistent sessions on all API replicas; an opaque cryptographically random session token with only its hash persisted; a `Secure`, `HttpOnly`, host-only cookie scoped to `/`. Choose SameSite=Lax to accommodate a normal cross-site OIDC GET callback and test supported response modes. Require a CSRF token and Origin checks for cookie-authenticated mutations. Rotate at login and privilege changes; invalidate on logout, account disable, credential reset, and security-version changes. Set configurable idle and absolute expiry. Persist accounts/sessions separately from task data so replay, import, retention, and ingester-leader changes cannot erase or duplicate identity state.

**Documented:** OWASP recommends salted Argon2id with at least 19 MiB memory, two iterations, and parallelism one; benchmark stronger parameters and upgrade hashes over time. NIST requires at least 15 characters for single-factor passwords, supports at least 64, forbids arbitrary composition rules and periodic forced changes, and requires compromised/common-password blocking and account-level failed-attempt rate limiting. NIST describes salted password hashing but does not thereby certify Argon2id for FIPS use. [Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [NIST §§3.1.1, 3.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html)

**Recommendation:** closed registration and administrator-managed local accounts; generic login errors, shared account/IP throttling, bounded concurrent hashing work, and audited reset/disable operations. An optional initial administrator is a one-time bootstrap supplied through a secret-backed environment variable, mounted secret file, or operator-generated credential, created atomically only before initialization. Support environment and file inputs with mutually exclusive sources; prefer file mounts where practical. Never ship a universal default password, expose unauthenticated first-user registration on a public installation, or recreate a deleted administrator on restart. Recovery should be an explicit operator procedure. These bootstrap choices are application recommendations, not OIDC features. Environment/file support was clarified in the design on 2026-10-03.

## OPA decision and operational contracts

**Documented:** named decisions use `POST /v1/data/{path}` with `{"input": ...}` and return the decision under `result`. An undefined document returns **HTTP 200 with `result` absent**. `strict-builtin-errors=true` turns builtin errors into fatal evaluation errors. Decision logging can add a `decision_id`. [REST API, Data API](https://www.openpolicyagent.org/docs/rest-api)

**Recommendation:** the backend first checks active identity and role grant, then calls a fixed configured decision path. Effective permission is **role grant AND valid OPA allow**; OPA cannot enlarge role grants. Define a versioned input/result schema. Require an exact boolean `allow=true`; missing/incorrectly typed results, timeout, malformed responses, unsupported schema, evaluation error, or unavailable policy must deny. Return an availability error for evaluation outages rather than pretend the user lacks a known permission. No side effects occur until authorization succeeds. Set a deadline and require policy readiness before serving protected requests.

**Documented:** OPA favors placing evaluation close to enforcement. Sidecars/node agents reduce latency and network dependence but consume resources per instance; central services share resources but need independent scaling and high availability. OPA supports native Go integration and Wasm; outside Go its documentation recommends a local daemon or sidecar. [Deployment](https://www.openpolicyagent.org/docs/deploy), [Integration](https://www.openpolicyagent.org/docs/integration)

**Recommendation:** support a local sidecar/process endpoint for Docker/VM/Kubernetes and a configurable remote authenticated endpoint for centrally operated or constrained installations. Every FastAPI replica enforces independently. Do not require Kubernetes. Embedding Wasm in Python is a separate project involving runtime, builtin parity, bundle distribution, and logging; do not present it as equivalent to a full OPA server.

**Documented:** snapshot bundles carry optional manifest revision and Rego version, support signature verification, and can persist for startup recovery. Signatures are not verified merely because bundles exist; verification must be configured. Persisted recovery is best effort. [Bundles](https://www.openpolicyagent.org/docs/management-bundles)

**Recommendation:** distribute reviewed signed snapshot bundles; pin immutable revision identifiers and verify signatures. Track installed revision/readiness on every replica. Define a maximum permitted policy age and rollback procedure; continuing with an approved last-known-good bundle is a separate freshness choice from allowing when evaluation fails. Avoid authorization-data caches that prolong user-disable or role-revocation delays. If caching decisions, bind keys to subject security version, action, resource attributes, policy revision, and expiry.

**Documented:** decision logs include input, result, and bundle revision. OPA evaluates `data.system.log.mask` before uploading/plugin delivery; masking may erase or replace paths. Remote OPA APIs need transport security, authentication, and endpoint authorization. `http.send` is a real outbound request builtin, and capabilities can constrain builtins/network hosts. [Decision Logs](https://www.openpolicyagent.org/docs/management-decision-logs), [OPA Security](https://www.openpolicyagent.org/docs/security), [Operations](https://www.openpolicyagent.org/docs/operations), [HTTP Builtins](https://www.openpolicyagent.org/docs/policy-reference/builtins/http)

**Recommendation:** send only trusted account/action/resource metadata to policies, omitting passwords, cookies, tokens, task argument bodies, result bodies, and traceback contents. Install an unconditional masking policy and test redacted logs. Audit decision ID, policy revision, account, action, resource ID, and mutation outcome; OPA decision logs do not prove a Celery operation executed. Restrict management APIs to operators, never browsers. Treat custom policy publishing as trusted code administration: restrict builtins/egress, size and evaluation time, validate schema, and run allow/deny fixtures before activation.

## Lists, live updates, fields, and aggregates

**Documented:** OPA partial evaluation can derive filters from known identity context and unknown resource attributes. Its current REST compile API exposes generic residual queries plus UCAST and SQL targets (PostgreSQL, MySQL, SQL Server, SQLite); it does not document a SurrealQL target. [Data Filtering](https://www.openpolicyagent.org/docs/filtering), [REST Compile API](https://www.openpolicyagent.org/docs/rest-api)

**Recommendation:** do not interpolate returned SQL into SurrealQL. Initially evaluate bounded batches of server-read resource metadata, authorize every candidate, and only emit permitted projected records. Apply an installation scope first. Use opaque cursors and a bounded scan budget; return fewer results when necessary. Never publish unauthorized total counts or raw scan offsets. For large-volume exact aggregates or pagination, require a separately specified, restricted filter language/compiler with parameterized SurrealQL and equivalence tests; unsupported policies must reject that query or use a complete bounded authorized scan, never silently weaken checks.

**Documented:** OWASP requires deny by default and permission checks on every request. Its API3:2023 guidance requires property-level authorization, explicit output fields, minimal response data, and schema validation. [Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [API3:2023](https://github.com/OWASP/API-Security/blob/master/editions/2023/en/0xa3-broken-object-property-level-authorization.md)

**Recommendation / inference:** hiding a field in output does not hide it if unauthorized users can filter/sort/group/search it and observe membership or counts. Reject such predicates unless a separate explicit permission grants that use. Build aggregates, graph links, exports, and chart buckets from authorized rows; never compute a global result and redact afterward. An arbitrary policy may make an exact count expensive or impossible within limits; deny/omit the feature explicitly. Reauthorize every live event, check current session/account state, invalidate subscriptions when policy or role versions change, and remove formerly visible rows without disclosing hidden payloads. Apply the same guarantees to snapshots, reconnect catch-up, imports, exports, and mutation responses.

## SurrealDB boundary

**Documented:** SurrealDB system users have root/namespace/database scope and built-in OWNER/EDITOR/VIEWER roles. Table/field `PERMISSIONS` apply to record users and permitted guests, **not system users**. Tables default to NONE; fields default to FULL. Capabilities govern guests, scripting, networking, and other features and must be configured on the server for remote clients. [Users](https://surrealdb.com/docs/learn/security/authentication/users), [Permissions](https://surrealdb.com/docs/learn/security/authorization/permissions-and-row-level-security), [Capabilities](https://surrealdb.com/docs/learn/security/authorization/capabilities)

**Recommendation:** remove browser raw database HTTP/WebSocket/RPC access and all browser database credentials. Route reads and live updates through typed FastAPI APIs, with OPA enforcement and explicit field projection. Keep SurrealDB private; disable guests and unused capabilities. Separate schema-provisioning, ingestion, query, and auth-control credentials/databases; use the least scope and role each requires. Database-scoped system accounts still bypass row permissions, so server enforcement remains mandatory. Record-user permissions can add defense in depth, but supporting arbitrary Rego restrictions would require another audited translation/enforcement design.
